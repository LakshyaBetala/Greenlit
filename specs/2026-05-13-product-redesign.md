## 1. The wedge (locked, do not re-debate)

**One-liner:** *"Live, continuous AI red-team for AI-built apps."*

**The 5-attribute corner only Greenlit can occupy:**

| Capability | Rafter.so | Rismon.ai | Greenlit | Snyk | CodeRabbit |
|---|:---:|:---:|:---:|:---:|:---:|
| Live URL probing (real attacks) | ❌ | ❌ | ✅ | ❌ | ❌ |
| Continuous monitoring (hourly + push) | ❌ | ❌ | ✅ | ✅ | ✅ PR-only |
| Real auto-fix PRs (not just prompts) | ❌ | ❌ | 🟡 → ✅ | 🟡 | ❌ |
| Non-tech founder UX | ❌ | ✅ | ✅ | ❌ | ❌ |
| AI-built-app focus (Lovable/Bolt/Cursor) | ❌ | ✅ | ✅ | ❌ | ❌ |

Only Greenlit can check all five. Every product, pricing, copy, and design decision must sharpen — not dilute — this combination.

**ICP:** Non-technical founders who built their app on Lovable, Bolt, Cursor, Replit, Windsurf, or v0. They have 10–500 users, no security training, and no budget for a $300/hr consultant.

**Job-to-be-done:** *"Tell me — in 60 seconds — whether my app is one bug away from a public incident, and fix the bug for me."*

The single most important screen. Replaces today's Bento Grid.

│  ─ one-line subhead with concrete proof            │
│  ─ primary CTA + secondary link                    │
├────────────────────────────────────────────────────┤
│  Zone 2: DOCTOR'S REPORT  (persistent nav rail)    │
│  ┌────────┬─────────────────────────────────────┐  │
│  │ Rail   │ Main panel — changes by section    │  │
│  │        │                                     │  │
│  │ Verdict│  Each breach is a card:             │  │
│  │ Breaches│   ─ severity pill                  │  │
│  │ Arch   │   ─ title + file:line              │  │
│  │ Stack  │   ─ Zone 3 (proof) inline          │  │
│  │ Fixes  │   ─ "Fix it" CTA                   │  │
│  │ Share  │                                     │  │
│  └────────┴─────────────────────────────────────┘  │
├────────────────────────────────────────────────────┤
│  Zone 3: BREACH PROOF  (terminal screenshot)       │
│  ─ shown inline in each card when severity ≥ high  │
└────────────────────────────────────────────────────┘

### 2.2 Zone 1 — Verdict Cinema (the share-card moment)

**Layout:**
- Full-bleed background with subtle gradient. Red tint when verdict = `do_not_ship`, amber when `ship_cautiously`, green when `ready_to_ship`.
- Vertical centering of content. ~70vh height. Below is "scroll for detail" hint.

**Content:**
- **Verdict pill** (top, small, all-caps, 11px): `DO NOT SHIP` / `SHIP WITH CAUTION` / `READY TO SHIP`.
- **Headline** (one sentence, 36–48px on desktop): *"3 critical breaches. Your /admin endpoint is open to the internet."*
- **Subhead** (one line, 16px, secondary color): *"We accessed your user table in 3.2 seconds. Here's the proof."*
- **Primary CTA** (large, branded): *"Show me the breach →"* — anchor-scrolls to first breach in Zone 2.
- **Secondary link** (text-only): *"View full report"* — scrolls past Zone 1.

**Rules:**
- The headline is generated by Sonnet 4.6 with a tight prompt — see §6.1. Never generic.
- When verdict = `ready_to_ship` (green), headline becomes *"Your app passes. Ship it."* + a green checkmark. No fake findings to be dramatic.
- Verdict pill color is the ONLY use of red/amber/green in the page. Reserve those for status.

### 2.3 Zone 2 — Doctor's Report (depth on demand)

**Layout:**
- Sticky left rail (200px wide on desktop, collapses to hamburger on mobile).
- Main panel takes remaining width.
- Rail sections (in order): Verdict, Breaches (count badge), Architecture, Tech Stack, Fix Plan, Share Report, Watch This App.
- Active section highlighted in green-dim background.

**Breaches main panel:**
- Stacked cards, one per finding, ordered by severity → file path.
- Each card: severity pill, title, file:line, plain-English description, Zone 3 proof (inline), fix CTA.
- Severities: `critical` (red), `high` (amber), `medium` (yellow-dim), `low` (gray). Anything below medium is collapsed by default.

**Architecture main panel:**
- Mermaid diagram from existing `architecture.mermaid_code` field.
- Below: connections list (existing data structure, unchanged).

**Tech Stack main panel:**
- Existing data, rendered as a clean table not pills (founders ignore pill clouds).

**Fix Plan main panel:**
- Ordered list of all breaches with auto-fix availability + CTA per item.
- "Apply all" button at top (paid feature — opens PR with all fixes).

**Share Report main panel:**
- Public link generator + preview of OG image.
- Embed badge code snippet (markdown + HTML).
- See §4 (Greenlit Bot + distribution loop).

**Watch This App main panel:**
- Connect-repo flow for continuous monitoring (paid).
- Shows last 10 scan deltas if already watching.

### 2.4 Zone 3 — Breach Proof (the undeniable evidence)

Inline inside each severity ≥ high breach card.

**Layout:**
- Monospace terminal block. Black background. Green-on-black for prompts, white for normal output, red for `HTTP 200` when 200 means breached.
- Top label: `THE EXPLOIT`.
- Body: actual curl command + actual response excerpt (truncated, with `...` for length).
- Bottom: `Proof captured 2026-05-13 at 14:32 UTC`.

**Example (for an open admin endpoint):**

```
THE EXPLOIT
$ curl https://myapp.lovable.app/admin/users
→ HTTP 200
{
  "users": [
    { "email": "user1@gmail.com", "id": 1 },
    { "email": "lakshya@example.com", "id": 2 }
    ...
  ]
}
Proof captured 2026-05-13 at 14:32 UTC
```

**Rules:**
- When `dast_service.py` couldn't capture a real exploit (e.g., target URL not provided, DAST disabled, finding came from static analysis), Zone 3 falls back to a code excerpt with file:line. Never fabricate.
- Real-data PII in proof must be redacted before display (`gmail.com` → `g***.com`).

### 2.5 Tone of voice

- **Verdict copy:** declarative, short, no jargon. *"Your login is broken."* not *"Authentication mechanism appears vulnerable to CSRF."*
- **Plain-English mode by default.** Power-user technical detail in collapsed `[show technical]` toggles.
- **Never apologetic.** *"We found 3 critical issues"* not *"We may have detected potential issues."*
- **First-person plural ("we") for Greenlit.** Founder is "you." Never use "the user."
- **Calm, factual, inevitable. NOT cinematic / hacker-themed.** The best security tools feel like an X-ray, not a horror film. No skull icons, no fake-terminal aesthetics beyond Zone 3 evidence, no "h4ck3r" vibes, no animated glitch effects. We are the calm CTO, not the dramatic pentester. If a screenshot of our verdict looks like a fake-news graphic, we've gone too far. Test: would Stripe ship this tone? If no, retune.

#### The 10 no-AI-slop rules (enforced on every shipped UI surface)

1. **No gradient backgrounds where solid color works.** The verdict cinema's subtle red/amber/green tint is the only exception. Nothing else gets gradients.
2. **Zero emoji in product copy.** Ever. One 🚀 makes us look like a hackathon project. Headlines, buttons, alerts, errors — all emoji-free.
3. **No glow, no neon, no synthwave aesthetics.** Visual restatement of the calm-CTO rule above.
4. **System fonts only.** Inter, SF Pro, Geist, system-ui. No display fonts, no AI-generated cursive, no Google Fonts that scream "vibe coder."
5. **Tables for data, never pill clouds.** Vulnerability lists, tech stack, pricing comparison — all tables. Pills only for status (severity badges, verdict pill).
6. **One primary CTA per screen.** No decision soup. Secondary actions are text links, not buttons.
7. **Concrete numbers, never vague claims.** Never "fast" — say "60 seconds." Never "secure" — say "14 attacks against your live URL." Never "many users" — say "1,247 apps."
8. **No fabricated testimonials in v1.** We don't have real ones yet. An empty testimonial section is better than fake quotes. Add testimonials only when real customers approve them in writing.
9. **Loading states show what's running**, never a generic spinner. The 5-step `ScanProgress` is the template — every other long operation must follow this pattern.
10. **Empty states have real next-action text**, not placeholder lorem. "Paste a GitHub URL to start your first scan" — not "Get started!" or 🚀.

### 2.6 Loading state (the 60-second wait)

Today: spinner + "analyzing." Boring. Users bail.

New: a 5-step animated reveal showing what's happening, with concrete updates:

```
[████░░░░░░] Step 1/5 — Cloning your repo (4,217 files)
[████████░░] Step 2/5 — Reading your code (Sonnet 4.6)
[████████░░] Step 3/5 — Attacking your live URL (14 checks)
[████████░░] Step 4/5 — Comparing to 10,000+ AI-built apps
[██████████] Step 5/5 — Writing your report
```

Each step shows real, evolving counters (file count, attack count, etc.). The "attacking your live URL" step adds anticipation. Total time still ~60s but feels active.

## 3. The "what do I do now" flow (work-stream #3)

After the verdict, the founder must have **at most four clear actions**, no more.

| Action | Path | Tier |
|---|---|---|
| **Fix it for me** | Greenlit opens an auto-fix PR for the selected breach | Free (1 fix), Indie (all) |
| **Send to Cursor** | Copy structured prompt with finding + fix to clipboard | Free |
| **Share this report** | Public report page + OG image + embeddable badge | Free |
| **Watch this app** | Connect repo for continuous monitoring + alerts | Solo+ |

### 3.1 "Fix it for me" UX

**Free tier:** Founder can apply ONE auto-fix per scan, ever. After clicking, Greenlit opens a real PR on their repo. PR title format: `[Greenlit] Fix: <breach title>`. PR body has: proof of exploit, the diff, "Tested by Greenlit's DAST on commit XXX." Founder reviews + merges manually.

**Paid tier:** "Apply all fixes" opens one PR with all fixes batched, plus continuous monitoring keeps watching.

**Risk:** Auto-fix can break code. Mitigations: (a) Only fix breaches with high-confidence patterns. (b) Each PR runs the existing test suite via GitHub Actions before merge. (c) Sonnet 4.6 generates the diff; we never edit without LLM-generated context. (d) Founder always reviews — PR is opened, not auto-merged.

**v1 supported auto-fix types (high-confidence patterns ONLY — do not generate PRs for anything else):**

| Type | Why it's safe to auto-fix |
|---|---|
| Missing auth middleware on admin/internal routes | Mechanical insertion of `@require_auth` decorator |
| Hardcoded API keys / secrets / tokens in source | Replace with `os.getenv()` + add to `.env.example` |
| Missing rate limiting on `/auth`, `/api/*` endpoints | Mechanical insertion of `slowapi` decorator |
| CORS wildcard / over-permissive origins | Constrain origin list to declared frontend URL |
| Unsafe admin routes (debug endpoints, swagger UI exposed in prod) | Gate behind env-flag or remove |
| Missing security headers (CSP, HSTS, X-Frame-Options) | Mechanical header injection in middleware |

**v1 EXPLICITLY out of scope (we surface the finding but show "Manual fix — copy to Cursor" instead of "Fix it for me"):**

- Business logic changes
- Authentication flow refactors (OAuth, SSO, JWT issuance, password reset)
- Database migrations or schema changes
- Stateful architecture rewrites
- Multi-file refactors that change function signatures
- Anything that requires existing tests to be updated to match

This narrow scope is non-negotiable for v1. Trust collapses faster than it builds — one broken PR on a real founder's repo and the bot loop dies. We expand the supported list only after v1 hits ≥85% merge rate on the narrow list.

### 3.2 "Send to Cursor" UX

Click button → clipboard now contains a structured prompt:

```
I'm using Greenlit to audit my app. Here are the findings, please fix them in my codebase:

[Finding 1 — Critical]
File: app/admin/users.py:14
Issue: Admin endpoint has no auth middleware
Fix: Add @require_auth decorator

[Finding 2 — High]
...

Apply these fixes carefully, run my tests, and ensure no regressions.
```

This is the bridge to Cursor/Copilot users who don't want auto-PRs.

### 3.3 "Share this report" UX

- Generates public URL: `greenlit.app/report/<scan_id>`.
- OG image auto-generated: verdict pill + headline + breach count + Greenlit logo. Founders share this on Twitter.
- Embed badge: `<img src="https://greenlit.app/badge/<repo>.svg">` shows live score (e.g., "Greenlit: 38/100"). Founders put it on their README to *prove* they care about security (vanity loop).
- Public report omits proprietary code (only file paths + descriptions, never code excerpts unless founder opts in).

### 3.4 "Watch this app" UX

- Connect GitHub repo via GitHub App (real OAuth, not query-string token — fix the existing security smell).
- Optional: provide live URL for continuous DAST polling.
- Frequency: every push (webhook) + every 6 hours (DAST tick).
- Alert channels: email (free), Slack/Discord (Indie tier).
- Each alert links to a fresh scan diff page.

## 4. Distribution: Greenlit Bot (work-stream #4)

The one viral loop. Acquisition by demonstration.

### 4.1 The mechanic

1. **Crawler** scans public GitHub for repos matching AI-coded signatures:
   - Lovable: `supabase` import + specific RLS patterns + `lovable.dev` in commit messages
   - Bolt: `app/` structure + `package.json` with specific dependencies + `bolt.new` URL in README
   - Cursor: commit author = "cursor[bot]" or Cursor-generated commit message patterns
   - Replit: `.replit` config file present
   - v0: `v0.dev` references in package.json

2. **Scorer** runs a fast Haiku 4.5 scan on each match. If finds ≥1 critical vuln, mark for outreach.

3. **PR generator** opens **one** real PR with:
   - Title: `[Greenlit] Fix: <one critical vuln>`
   - Body: proof-of-exploit (curl + response), the diff, link to full report at `greenlit.app/scan/<id>`
   - Branch name: `greenlit/fix-<vuln-slug>`
   - Author: GitHub App "Greenlit Bot"

4. **Landing page** at `greenlit.app/scan/<id>` shows the founder THEIR full report (their repo, their findings) and pitches the upgrade.

### 4.2 Quality rules (non-negotiable — GitHub will ban a spammy bot)

- **One PR per repo. Ever.** If closed, never re-open.
- **Opt-out is sacred.** README sentinel `<!-- greenlit:off -->` or label `greenlit-no-thanks` blocks the bot forever.
- **Only critical findings.** No "you should rename this variable" PRs. The bar is "this is exploitable."
- **Diff must apply cleanly.** Tested on a fork before opening the PR.
- **Author footer must identify Greenlit clearly,** with a "this was sent automatically, here's why and how to opt out" sentence.
- **Only fix types from §3.1 narrow list.** Bot does not pioneer new fix patterns — it only ships fixes already proven in the dashboard auto-fix flow.

### 4.2.1 Phased rollout (do not skip phases)

| Phase | Duration | What automation does | What humans do |
|---|---|---|---|
| **Phase 0** | Weeks 1–2 | Nothing automated | Manually hand-build the first **100 PRs** on hand-picked public Lovable/Bolt apps. Verify: PR opens cleanly, diff applies, founder responds positively or neutrally (not hostile). |
| **Phase 1** | Weeks 3–6 | Bot finds candidates and drafts PR locally; queues for human approval. | Review queue daily, approve/reject. Watch acceptance rate. |
| **Phase 2** | Week 7+ | Fully automated — bot opens PRs without human approval. | Spot-check 10% sample weekly; monitor abuse reports. |

**Gates to advance phases:**
- **Phase 0 → Phase 1:** ≥60% of 100 hand-built PRs received a positive/neutral response (merged, commented constructively, or no response within 14 days = neutral). Zero GitHub abuse reports.
- **Phase 1 → Phase 2:** ≥40% merge rate on the next 200 queued PRs. Zero GitHub abuse reports. Zero unsubscribe/opt-out rate above 5%.

If a gate fails, stay in the current phase and diagnose. **Never skip phases to move faster.** GitHub bans are permanent.

### 4.3 Unit economics

- Cost per acquisition (standard, no batch): 1 Sonnet pre-screen ($0.075) + 1 Haiku verification ($0.005) + GitHub API (free) ≈ **$0.08**.
- Cost per acquisition (with batch — Bot is 100% async background, perfect fit): **~$0.04**.
- If 1 in 50 founders converts to Solo $7/mo, that's $7 first-month revenue per ~$2 acquisition cost on the batch path.
- At 6-month retention average: LTV $42, CAC $2, **LTV/CAC ≈ 21**. Very healthy.
- Cap monthly Bot budget at $500 → ~12,500 outreach PRs (batch path) → at 2% conversion ≈ **250 paid users/month from Bot alone**.

### 4.4 First-launch plan

- Week 1: Hand-build PRs for the top 20 most-starred public Lovable apps. Verify the experience works end-to-end. Tweet the results.
- Week 2–4: Open the bot to public Lovable apps detected by signature.
- Month 2: Expand to Bolt + Cursor + v0.

## 5. Pricing (work-stream #5)

### 5.1 Tier structure

| Tier | Standard | India | Emerging | What you get |
|---|---|---|---|---|
| **Free** | $0 | ₹0 | $0 | 10 deep scans/mo on public repos (3/day hard cap). Verdict + **top 5 vulns visible** (rest behind paywall). 1 DAST probe per scan. 1 on-demand auto-fix per scan. Share badge + public report. Same-URL re-scan returns the cached result instantly (24h cooldown — does not burn quota). |
| **Solo** | **$7/mo** | **₹299/mo** | **$5/mo** | 50 deep scans/mo (10/day cap). All vulns visible. Unlimited DAST probes. 1 private repo. Continuous monitoring (every 6h). Email alerts. Unlimited on-demand auto-fixes. Copy-to-Cursor prompts. |
| **Indie** | **$29/mo** | **₹999/mo** | **$19/mo** | 300 deep scans/mo (no daily cap). 10 private repos. **Automatic auto-fix on every push** (no clicks — Greenlit opens PRs as breaches appear). Webhook + hourly monitoring. Slack/Discord alerts. Priority Sonnet 4.6 queue. 3 team seats. Read-only API access. |
| **One-time scan** | **$5** | **₹399** | **$3** | Single deep audit + downloadable PDF + 30-day result access + 1 on-demand auto-fix. Use case: "founder about to launch, will not subscribe." |

See §5.4 for geo-band assignment logic and §5.6 for the full rate-limit matrix.

**Auto-fix tier semantics (concrete):**
- **Free / one-time:** 1 click → 1 PR per scan. Capped.
- **Solo:** N clicks → N PRs. You're still the trigger.
- **Indie:** Greenlit is the trigger. New breach detected → PR opens automatically.

### 5.2 Psychology behind the structure

- **Anchoring:** Indie ($29) is shown first on the pricing page so Solo ($7) feels obvious. Free is shown last.
- **Loss aversion:** Free tier explicitly says "your app is scanned ONCE — if something breaks tomorrow, we won't know." Drives upgrade.
- **One-time scan is the genius pricing move.** Captures the impulse-buy founder who won't subscribe but WILL pay $5 to know if they're about to ship a breach. Most of them upgrade to monitoring later.
- **No "Enterprise — contact us" tier yet.** Adds zero revenue at this stage, dilutes positioning.

### 5.3 Free-tier rules (the conversion gate)

- Free user sees the verdict + top 3 breaches in full. **Breaches 4+ show as locked cards** with: severity pill, blur, "Unlock to see what else is broken — $7/mo or one $5 scan."
- Free user gets exactly 1 on-demand auto-fix per scan. (Today's codebase ships 0 working auto-fixes — the service is stubbed. Wiring this up is on the implementation critical path because it powers the free-tier "wow" moment.) Founder sees auto-fix WORK, then upgrades for unlimited.
- Free user CAN share the report publicly — this is the viral loop, do not gate it.
- Free user CANNOT enable continuous monitoring or webhook scans — this is the Solo upgrade.

### 5.4 Geo pricing — three bands by IP

Country detected from the `CF-IPCountry` request header (free, populated automatically when behind Cloudflare proxy). Fallback to `X-Country` header for non-CF deploys. Default to "Standard" when neither is set (defensively avoid accidental discounts on misconfigured deploys).

**Band assignment:**

| Band | Countries | Why |
|---|---|---|
| **Standard** | US, CA, GB, IE, AU, NZ, JP, SG, HK, CH, IL, AE, EU-27 | High-GDP markets willing and able to pay $7–29 |
| **India** | IN only | Distinct payment infrastructure (Razorpay/UPI), large enough TAM to deserve its own price point |
| **Emerging** | every other ISO country code | Flat 30% discount band — captures price-sensitive markets (BR, MX, ZA, PH, ID, TR, NG, VN, EG, etc.) without maintaining 50 separate currency price lists |

**Payment routing:**
- `India` → Razorpay subscription in INR. Existing `app/api/payments.py` flow.
- `Standard` + `Emerging` → Stripe Checkout in USD. Separate Stripe price IDs per band (e.g. `STRIPE_PRICE_SOLO_STANDARD_USD` and `STRIPE_PRICE_SOLO_EMERGING_USD`). Stripe handles local payment methods (UPI, OXXO, iDEAL, etc.) automatically inside each Checkout Session — no extra integration needed.

**Why three not fifty:** 90% of conversion comes from Standard or India. Emerging is one flat tier — a 30% discount on top of Standard — and Stripe's localized payment methods do the heavy lifting for the actual currency UX. Maintaining one Emerging price line beats maintaining 50 country-specific ones.

**Detection failure cases:**
- Header missing → Standard (avoid accidentally discounting US/EU traffic).
- Behind Cloudflare → `CF-IPCountry` is set automatically.
- Direct deploy without CF → set `X-Country` from your edge/CDN, or users get Standard pricing by default.

### 5.5 Pricing page UX

- USD ↔ INR toggle at top right.
- Indie card has subtle "Most popular" badge.
- Below tier cards: 4-row comparison table.
- Below comparison: 3 testimonials (start with 1 real + 2 placeholders flagged for replacement post-launch).
- Bottom: FAQ. Last FAQ is "What if I just want one scan?" → leads to the $5 one-time.

### 5.6 Rate-limit matrix (the conversion gate)

| Limit | **Free** | **Solo** | **Indie** |
|---|---|---|---|
| Deep scans per month | **10** | 50 | 300 |
| Deep scans per day cap | 3 | 10 | none |
| Same-URL re-scan cooldown | 24h (cached) | 1h | none |
| DAST live probe runs per scan | 1 | unlimited | unlimited |
| Continuous monitoring | ❌ | ✅ every 6h, 1 repo | ✅ every push + hourly, all repos |
| Private repos | ❌ | 1 | 10 |
| On-demand auto-fix | 1/scan | unlimited | unlimited |
| Automatic auto-fix on push | ❌ | ❌ | ✅ |
| Vulnerabilities shown in result | top 5 only | all | all |
| Email alerts | ❌ | ✅ | ✅ |
| Slack/Discord alerts | ❌ | ❌ | ✅ |
| Read-only API access | ❌ | ❌ | ✅ |

**Free-tier rationale — the conversion design:**

- **10 scans/mo, not 1.** The "1 scan/month" trap kills the funnel. Founder scans their app, sees value, can't test a friend's app or re-scan after a fix, forgets us. 10 scans = ~$0.75/month worst-case acquisition cost per heavy free user. Affordable for what could become a $7+/mo conversion.
- **3 per day hard cap** prevents abuse — scripted scanning of 100 random repos is the failure mode.
- **Same-URL 24h cooldown** is silent-good UX: rescanning the same repo doesn't burn quota AND returns the cached result instantly. Better feel.
- **Top 5 vulns visible** is the paywall gate: founder sees enough findings to believe the product is real, then hits a clearly-counted lock on vuln #6+ — *"`8 more vulnerabilities found — unlock for $7/mo or pay $5 once`."* This is the exact conversion moment.
- **1 free DAST probe per scan is non-negotiable.** The DAST live probe IS our differentiator from Rismon and Rafter; if free users never experience it, they don't understand why we're different and they don't convert.

**Anti-abuse enforcement (Sprint 7 implementation):**

- Rate limit by `(IP, user_id, repo_url)` — caps both anonymous and authenticated paths.
- Same-URL cache-hit returns the existing scan_id (no new resource consumed).
- Daily cap is the brake against scripted abuse; monthly cap is the conversion driver.
- Layer enforced in `app/api/repos.py` via slowapi (already installed) + a new `app/services/quota.py` for per-user tier-aware checks.

## 6. Technical foundations

### 6.1 Model stack

| Pass | Model | Why | Replaces |
|---|---|---|---|
| **Deep scan** (first audit, vuln descriptions, autofix diff) | **Claude Sonnet 4.6** | Strongest reasoning in tier; generates non-generic findings | Gemini 2.5 Flash (current) |
| **Monitoring tick** (hourly DAST classification, diff scans) | **Claude Haiku 4.5** | $0.001/poll — affordable hourly | Gemini Flash-Lite |
| **Bot pre-screen** (rapid yes/no on whether a public repo has a critical vuln) | **Haiku 4.5** | Cheap + decisive | n/a (new) |
| **Fallback chain** (if all Claude APIs fail) | Gemini Flash → Flash-Lite → 2.0-Flash → 2.0-Flash-Lite → 1.5-Flash → 1.5-Flash-8B | Never crash on quota exhaustion | unchanged |

Implementation: introduce `app/services/llm_router.py` that handles model selection + fallback. All services (`rag_service`, `dast_service`, `autofix_service`) call into the router, never instantiate clients directly. *(Status: shipped in commit `da13b9a`.)*

**Per-scan cost (Sonnet 4.6 deep scan, real measured numbers — not the earlier $0.15 estimate):**

| Mode | Input ~10K tokens | Output ~3K tokens | Total per scan |
|---|---|---|---|
| **Standard** | $0.030 | $0.045 | **$0.075** |
| **+ prompt cache** (repeat scans of same repo) | $0.027 | $0.045 | **$0.072** |
| **+ batch** (async work only — monitoring, Bot) | $0.015 | $0.0225 | **$0.038** |
| **batch + cache** | $0.014 | $0.0225 | **$0.036** |

User-facing deep scans stay synchronous → ~$0.075 each. Background monitoring + Bot pre-screens use batch → ~$0.04 each. Cost cap per scan = **$0.12 worst case** (bounded by §6.1a token caps).

Monitoring ticks (Haiku 4.5, ~5K in + 1K out): $0.010 standard, **$0.003 batch+cache.**

### 6.1a Token budget caps per tier

Hard ceilings prevent runaway cost from unusual or adversarial repos. Caps enforced at retrieval time (cap top-k chunks before constructing the prompt) — the model never sees more than the cap.

| Tier | Max input tokens / scan | Max output tokens / scan | Max scan cost |
|---|---|---|---|
| **Free** | 12,000 | 4,000 | **$0.10** |
| **Solo** | 20,000 | 6,000 | **$0.15** |
| **Indie** | 40,000 | 8,000 | **$0.24** |

Why caps differ by tier:
- Solo users pay $7/mo for sharper findings → larger retrieval window → better signal on big repos.
- Indie users pay $29/mo for the sharpest analysis → highest cap.
- Free tier still adequate for typical AI-built apps (5–30K LoC ≈ 25–150K raw tokens, retrieval brings it under 12K easily).

Implementation: add `MAX_INPUT_TOKENS_PER_TIER` and `MAX_OUTPUT_TOKENS_PER_TIER` constants in `app/config.py`. `rag_service.py` reads the user's tier and slices retrieved chunks accordingly before constructing the prompt. Tier-unknown (anonymous) gets the Free cap.

### 6.2 Gemini fallback robustness

Already implemented in `rag_service.py:235`. Keep the 6-model chain. Add: when all models fail, instead of returning `DEMO_REPORT`, return a real "scan_partially_failed" status with whatever findings were gathered from DAST (which doesn't depend on the LLM). This means the live-attack proof is ALWAYS available even if the LLM completely fails.

### 6.3 Continuous monitoring infrastructure

Today's `uptime_worker.py` only pings the production URL. Expand to a real monitoring engine:

- **Push events:** existing webhook in `app/api/webhooks.py` triggers diff scan.
- **Tick events:** new background worker runs every 6h per Solo+ user, fires DAST checks against their `production_url`.
- **Storage:** existing `scans` and `probes` tables in SQLite. Add `alerts` table.

### 6.3.1 Alert pipeline with confidence + dedup (the anti-noise design)

Every finding from a tick scan gets THREE values before being considered for alerting:

1. **Confidence score (0–100)** — Haiku 4.5 rates "how confident are we this is a real, exploitable issue, not a false positive?"
2. **Severity** — `critical` / `high` / `medium` / `low`
3. **Dedup hash** — `sha256(vuln_type + file:line + signature_pattern)`

**Alerting rules table:**

| Condition | Action |
|---|---|
| `severity=critical AND confidence ≥ 80` | Immediate alert (email, plus Slack/Discord for Indie) |
| `severity=high AND confidence ≥ 70` | Batched into daily digest email |
| `severity=medium OR confidence < 70` | Silent — surface in dashboard only, no notification |
| `dedup_hash` already alerted in last 24h | Suppress entirely |
| Per-user weekly cap exceeded (5 immediates, 1 digest) | Hold remaining alerts for next week |

**Why this matters:** alert fatigue is the #1 killer of monitoring products. Users who get 30 alerts a week stop opening any of them. Our cap is calibrated to fewer-than-Slack-DM frequency — every Greenlit alert should feel like it earned the founder's attention.

**Daily digest format (for high-severity batch + medium summary):**
- One subject line: "Greenlit: 2 new issues on myapp.lovable.app this week"
- One screenshot of the verdict pill in the email body
- Inline list of findings with one-line each
- Single CTA: "Review on Greenlit →"

### 6.4 Security hardening (the existing OAuth smell)

Current: `app/auth/github.py` returns the GitHub token as a query param → frontend stores in localStorage. Replace before launching v2:

- Token exchanged server-side, stored in an httpOnly + Secure + SameSite=Lax cookie.
- Frontend never sees the raw token.
- Sessions are signed JWTs with 7-day expiry, refresh on activity.

This change alone removes a `high`-severity finding from Greenlit's own scan of itself (which is currently being shipped as a deliberate joke in the demo report — kill that joke before launch, it stops being funny when paying customers find it).

### 6.5 Database expansion

Add columns/tables:

- `repos.production_url TEXT` — for continuous DAST polling.
- `repos.opt_out_bot BOOLEAN` — for Greenlit Bot opt-out.
- New table `alerts` (id, scan_id, repo_id, severity, delivered_to, delivered_at, dedup_hash).
- New table `bot_outreach` (id, repo_url, pr_url, pr_state, scanned_at, opened_at, closed_at, founder_clicked_at).

### 6.6 Anthropic rate-limit architecture (two-layer)

**Layer 1 — per-user limits (FastAPI level, slowapi):**

| Path | Limit |
|---|---|
| Anonymous scan requests | 10/min/IP |
| Free authenticated | 30/min |
| Solo authenticated | 60/min |
| Indie authenticated | no cap |

**Layer 2 — per-Anthropic-org limits (`llm_router.py` token bucket):**

Anthropic enforces per-org tokens-per-minute (TPM) and requests-per-minute (RPM) caps based on the org's tier:

| Anthropic tier | Deposit required | Sonnet in/out TPM | Sonnet RPM | Comfortable user load |
|---|---|---|---|---|
| Tier 1 (default) | $0 | 50K / 10K | 50 | ~10 active users |
| **Tier 2** | **$40** | 200K / 40K | 1,000 | ~100 active users |
| Tier 3 | $200 | 1M / 200K | 4,000 | ~1,000 active users |
| Tier 4 | $400 | 2M / 400K | 4,000 | ~5,000 active users |

**Recommendation: deposit $40 before public launch to start at Tier 2.** Negligible cost; removes the most likely day-one outage when traffic spikes.

**Token-bucket implementation (Sprint 7):**

Inside `llm_router.py`:

- Track consumed TPM (input + output separately) and RPM in a sliding 60s window.
- Size the bucket at **80% of the published cap** to leave headroom for spikes (160K input TPM at Tier 2, not 200K).
- When a request would exceed the bucket: queue with FIFO ordering, retry once headroom appears.
- On Anthropic 429 (despite our local limiter): exponential backoff (3s, 9s, 27s), then fall through to the Gemini chain (existing behavior).

**Per-tier priority queue (Sprint 7 nice-to-have):** Indie scans get bucket priority over Solo, Solo over Free. Implemented as separate FIFO queues drained in priority order when bucket headroom is available.

## 9. Open risks (named, not solved here)

1. **GitHub may flag the Bot as spam** if outreach feels low-quality. **Mitigation:** §4.2 strict rules + §4.2.1 phased rollout (no full automation before week 7 + acceptance-rate gate).
2. **Auto-fix PRs may break user code.** **Mitigation:** §3.1 narrow supported-types list (6 high-confidence patterns only) + manual founder review on every PR + CI test gate + never auto-merge.
3. **Sonnet 4.6 cost overrun on free tier.** **Mitigation:** hard cap 1 deep scan/month/free user. Bot pre-screen uses Haiku ($0.005). Monthly budget cap = $500 on the bot loop.
4. **Monitoring alert fatigue** — users tune out if we cry wolf. **Mitigation:** §6.3.1 confidence-gated alerting + dedup window + per-user weekly cap (5 immediates, 1 digest).
5. **Rismon launches "live probing"** in response. **Mitigation:** ship continuous monitoring + auto-fix before they can build it. ~3-month head-start window.
6. **Tone too "cinematic" / hacker-aesthetic** alienates non-tech founders. **Mitigation:** §2.5 tone rules (calm CTO, not dramatic pentester) + Stripe-tone test before every shipped surface.
7. **Underestimated SaaS infra complexity** — this is no longer a side project. Real systems: ingestion, scanning, DAST, LLM routing, PR generation, webhooks, monitoring, alerting, public reports, payments, auth, bot. **Mitigation:** v2 sequence in §7 ships the smallest viable surface; deferred features stay deferred until traction supports the next layer. Hire decision in 6 months if MRR ≥ $5K.
